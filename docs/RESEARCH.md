# 今日热搜 · 需求研究

本文档记录今日热搜项目从 0 开始做 research 的过程。它不是 PRD，也不是技术设计，而是帮助产品和工程判断：为什么要做、先做什么、哪些结论已经验证、哪些仍是假设。

为了让流程更接近真实软件开发，本文把研究拆成两个阶段：

- PRD 前研究：先用产品视角确认用户、问题、场景和产品机会。
- PRD 后研究：再用工程视角验证 PRD 草案的技术和数据可行性。

推荐顺序：机会研究 -> 场景研究 -> 参考研究 -> 产品假设 -> MVP 草案 -> 可行性研究 -> PRD 冻结。

## 1. 机会研究

目标：确认要解决的问题，而不是一开始确认功能。

### 需要回答的问题

- 谁会打开这个网站？
- 他打开网站时正在做什么？
- 他为什么不直接分别打开微博、知乎、B 站？
- 他最想节省的是时间、注意力，还是信息查找成本？
- 这个项目除了学习全栈，还有没有真实使用价值？

### 用户是谁

MVP 主用户是想快速扫热点的普通访客，包括学生、上班族和轻度资讯浏览者。

内容创作者可能会使用热点做选题参考，但不是 MVP 的主用户。面试官或项目评审者是项目展示受众，不作为产品功能取舍的主要依据。

### 用户问题

用户想快速了解多个平台正在发生什么，但不想分别打开多个 App 或网页。

核心问题不是“没有热榜”，而是“多个平台热点分散，横向比较麻烦”。

### 产品机会

做一个无需登录、打开即看的多平台热点聚合页，让用户在一个页面看完多个平台当前热点。

## 2. 使用场景

目标：把抽象用户变成具体使用场景。

### 需要回答的问题

- 用户什么时候打开？
- 一次浏览会停留多久？
- 他是扫一眼，还是深入分析？
- 他会不会点击跳转原平台？
- 他失败时能不能接受部分平台不可用？

### 场景 A：快速浏览

用户打开首页，在 30 秒内扫完多个平台 Top 10。

### 场景 B：横向比较

用户想知道不同平台是否在讨论同一事件。

### 场景 C：点击详情

用户看到感兴趣标题后，跳转原平台查看详情。

### 当前判断

- 用户主要是快速扫读，不是深度搜索。
- 首页应该直接展示内容，不需要营销页。
- 单个平台失败时，其他平台仍然要能看。

### 需要观察的问题

- 类似热榜聚合页如何布局？
- 每个平台榜单是否放在卡片里？
- 每条信息展示哪些字段？
- 更新时间、来源、异常状态怎么表达？
- 移动端如何排版？

### 调研输出要求

- 每个对象至少记录 3 条具体观察。
- 每条观察要能反推出产品决策，例如“是否使用卡片”“是否展示热度”“是否需要更新时间”。
- 如果只是个人偏好，标记为“主观判断”；如果来自页面事实，标记为“页面观察”。
- 调研结束后，把可借鉴内容合并为本项目的页面原则。

### 信息结构

多个平台适合用卡片分区展示。卡片标题展示平台和榜单名，卡片内容展示该平台的 Top 列表。

### 单条内容字段

排名和标题是必需字段；外链用于跳转原平台详情。热度字段在不同平台之间不一定稳定，应作为可选字段。

### 页面风格

采用新闻热榜风格，重点是清晰、可扫描、少干扰。页面应偏信息看板，不做复杂社区、推荐流或营销落地页。

## 4. 产品假设

目标：把 research 变成可讨论的 PRD 草案，但在验证前不要写成最终结论。

- 假设展示 3 个主流平台，已经能满足最小使用价值。
- 假设 Top 10 比完整榜单更适合快速浏览。
- 假设用户更需要稳定可读，而不是复杂筛选。
- 假设无需登录可以降低访问门槛。
- 假设点击跳转原平台比站内详情页更适合 MVP。

## 5. MVP 草案

以下内容是从产品研究推导出的 MVP 草案。它应先经过可行性研究，再进入正式 PRD。

- 首页展示微博、知乎、B 站三张热榜卡片。
- 每个平台展示 Top 10。
- 每条展示排名、标题、链接，热度可选。
- 页面提供刷新入口。
- 单个平台失败不得影响其他平台。
- 页面可通过公网 HTTPS 访问，适合作为公开展示项目。

### 数据源

验证微博、知乎、B 站是否有可访问、可解析、相对稳定的数据源。

当前状态：页面访问已初步验证；微博、知乎、B 站均找到可由后端请求的候选数据入口。微博和 B 站返回直接 JSON；知乎当前候选入口返回“热搜词”，不是问答内容热榜。Owner 已确认 MVP 接受知乎热搜词，并将 B 站卡片命名为“B 站热门”。

执行流程：

1. 先打开平台原始榜单页面，确认普通访客是否可以访问。
2. 记录页面入口、榜单名称、是否需要登录、是否有明显反爬或访问限制。
3. 查找是否存在可被后端请求的 JSON 数据来源；优先使用公开页面背后的 JSON，不使用需要密钥的私有接口。
4. 用后端视角判断：如果只能浏览器访问但后端无法稳定请求，标记为“不可直接作为后端数据源”。
5. 每个平台至少在两个不同时间点重复验证一次，避免把偶发成功当成稳定能力。
6. 将结果填入可行性记录表，并标记“通过 / 不通过 / 待定”。

通过标准：

- 普通访问不需要个人账号 Cookie。
- 后端可以请求并解析。
- 至少能得到 Top 10。
- 数据源失败时可以被捕获为该平台失败，而不是导致整个接口失败。

### 字段

验证每个平台是否能稳定拿到 `rank`、`title`、`url`，以及 `heat` 是否稳定。

当前状态：三个平台都能初步映射 `rank` 和 `title`；`url` 需要按平台规则生成或取接口字段；`heat` 只能作为可选字段。

执行流程：

1. 从每个平台抽取至少 10 条样例。
2. 给每条样例标注原始字段名和目标字段名。
3. 检查标题是否完整、链接是否能跳转原平台、排名是否可确定。
4. 检查 `heat` 是否每条都有、含义是否一致、单位是否稳定。
5. 如果某字段在一个平台缺失，判断是平台特性还是解析问题。

通过标准：

- `rank`、`title`、`url` 三个字段均可稳定映射。
- `heat` 如果不稳定，只能作为可选字段，不能进入必须验收标准。
- 原平台链接可点击，不生成无法访问的假链接。

### 前后端边界

验证前端是否能直接请求上游平台。如果存在 CORS、鉴权、限流或稳定性问题，则必须由后端中转。

当前状态：按自建后端中转方向设计，前端不直接请求上游平台 API。

执行流程：

1. 用浏览器访问原始页面，确认用户侧可见内容。
2. 用后端请求方式验证数据源是否可访问。
3. 判断是否存在 CORS、Cookie、Referer、User-Agent、频率限制等约束。
4. 如果前端直接请求存在不稳定或跨域问题，记录为“必须后端中转”。
5. 明确前端只请求自建接口，不直接请求微博、知乎、B 站等上游平台。

通过标准：

- 前端数据访问路径统一为自建后端接口。
- 上游平台访问逻辑只存在于后端服务中。
- 不需要在前端暴露密钥、Cookie 或敏感配置。

### 缓存

验证 5-10 分钟缓存是否能降低上游请求压力，同时保证数据不过旧。

当前状态：缓存时间作为初始假设，后续可按数据源稳定性调整。

执行流程：

1. 记录每个平台榜单内容变化频率。
2. 估算用户可接受的数据延迟，例如 5 分钟、10 分钟、30 分钟。
3. 对比上游稳定性和请求成本，判断是否需要不同平台不同 TTL。
4. 明确“更新时间”表示后端最近一次成功获取该平台数据的时间，不是用户点击刷新的时间。
5. 记录刷新失败时是否允许继续展示旧缓存。

通过标准：

- 默认 TTL 可以落在 300-600 秒。
- 每个平台可以独立缓存。
- 有旧缓存时，上游失败不会清空可读数据。
- 页面能区分“最新成功更新时间”和“当前刷新失败”。

### 异常处理

验证每个平台是否能独立失败、独立缓存、独立展示错误状态。

当前状态：单个平台失败不得影响其他平台，这是 PRD 和技术设计都需要保持的约束。

执行流程：

1. 为每个平台列出可能失败原因：网络失败、数据格式变化、空列表、访问受限、解析失败。
2. 分别判断有旧缓存和无旧缓存时页面应该怎么显示。
3. 验证后端是否能返回“部分成功”的结构，而不是一个平台失败就整体失败。
4. 验证前端是否能展示单平台重试入口。
5. 记录每种失败是否对应 `stale`、`error` 或 `empty` 状态。

通过标准：

- 一个平台失败不影响其他平台展示。
- 有旧缓存时展示 `stale`，不遮挡榜单内容。
- 无旧缓存时展示 `error`，并提供单平台重试入口。
- 请求成功但无内容时展示 `empty`，不伪造数据。

## 7. PRD 调整规则

可行性研究结束后，按以下规则决定是否修改 PRD：

- 如果某平台数据源不稳定，PRD 要改平台、降低承诺或明确风险。
- 如果 `heat` 不稳定，PRD 要明确 `heat` 是可选字段。
- 如果前端不能直接请求，PRD 和技术设计都要明确后端中转。
- 如果真实数据不可长期稳定获取，不能把长期 Mock 写成真实热榜。
- 如果某个失败场景无法可靠处理，需要重新定义页面状态和验收标准。

## 8. 文档验收标准

Research 本身不跑代码测试，但要做文档验收：

- 一个没有产品背景的工程师能读懂这个产品为什么要做。
- 能看出哪些结论来自用户场景，哪些结论来自技术验证。
- PRD 里的每个关键设计点，都能在 research 中找到来源或验证记录。
- 未验证内容必须标为“假设”或“待验证”，不能写成确定事实。
- 可行性失败时，文档能指导 PRD 如何调整。
