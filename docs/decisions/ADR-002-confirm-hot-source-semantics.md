# ADR-002：确认热点数据源语义

## 状态

已接受

## 背景

- 需求研究阶段验证到微博、知乎、B 站均存在可由后端请求的候选数据入口。
- 知乎候选入口返回的是“热搜词”，不是问答内容热榜。
- B 站候选入口返回的是“热门视频”，不是热搜词榜。
- 需要在进入技术设计和实现前确认 MVP 的产品口径，避免后续实现和页面文案偏离实际数据语义。

## 决策

- MVP 接受知乎使用“热搜词”数据，页面卡片命名为“知乎热搜词”。
- MVP 接受 B 站使用“热门视频”数据，页面卡片命名为“B 站热门”。
- 微博继续使用“微博热搜”口径。
- 前端仍只请求自建后端接口，不直接请求上游平台。

## 理由与权衡

- 三个平台都能提供无需密钥的候选数据入口，有利于保持 0 元、公开展示和学习项目定位。
- 知乎热搜词比问答内容热榜更容易稳定映射到统一字段，但缺少 heat。
- B 站热门视频比热搜词更符合当前可验证数据源，但页面必须避免误称“热搜”。
- 统一以 `rank`、`title`、`url` 为必填字段，`heat` 保持可选，可以兼容平台差异。

## 替代方案

- 继续寻找知乎问答内容热榜：产品语义更接近“热榜”，但数据源稳定性和后端可请求性尚未确认。
- 继续寻找 B 站热搜词榜：文案更统一，但当前已验证的公开视频热门接口更可靠。
- 改用第三方聚合 API：实现更快，但稳定性、版权边界和项目展示可信度更弱。

## 后果

- `docs/PRD.md`、`docs/TECH_DESIGN.md` 和 `docs/RESEARCH.md` 应同步使用“知乎热搜词”和“B 站热门”口径。
- 技术设计应记录对应数据源、字段映射和平台差异。
- 后续若要改回知乎问答内容热榜或 B 站热搜词榜，需要重新调研、请求 Owner 确认，并补充新的 ADR。
